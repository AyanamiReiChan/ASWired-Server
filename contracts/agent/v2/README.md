# Negotiated binary stream extension

The X25519/HKDF/AES-GCM v1 handshake and authentication remain unchanged. A new WebSocket Agent adds `stream: {version: 2, binary: true, compression: "gzip", telemetry_delta: true}` inside its first encrypted Report. Only the first encrypted Reply may select the extension, returning `version: 2`, `binary: true`, `heartbeat_seconds: 15`, `telemetry_seconds: 5`, and the offered optional features. Missing/unsupported offers keep the original v1 report/reply loop. Binary peers that do not select `telemetry_delta` keep full observations and the original Reply shape. HTTP Pull and Direct retain v1 and their existing cadence; they still benefit from compact JSON encoding. No reconnect-to-plaintext or unauthenticated downgrade is introduced.

After selection, both directions exclusively use WebSocket binary messages. Their format is `ASW2` (4 bytes), flags (1 byte, bit 0 = gzip; no other bits allowed), sequence (8 bytes, unsigned big endian), and AES-GCM ciphertext/tag. Nonces continue the same per-direction sequence used for the handshake. AAD is `aswired-agent-v1/binary-v2|` followed by the complete 13-byte header. The existing directional keys remain in use. The header, compression flag and sequence are authenticated; reordered/replayed frames are rejected.

Plaintext is JSON with HTML escaping disabled. Compression, when selected, is gzip level 1 before encryption, only for telemetry payloads of at least 1024 bytes and only when the compressed representation is smaller. The compressed and decompressed plaintext limits are 16 MiB. Malformed/truncated gzip, authentication failures, invalid flags, invalid JSON, unsupported message kinds and unexpected text frames terminate the stream. The WebSocket compression extension is not used.

Client updates have `kind`, Unix-second `timestamp`, optional `busy`, and kind-specific fields:

- `heartbeat`: no observations/capabilities/results, emitted independently every 15 seconds.
- `telemetry`: samples every 5 seconds, preserving accounting and behavior-rule sampling. Capabilities are included only when changed. Peers without `telemetry_delta` send full `observation`; negotiated peers use the cumulative-value delta protocol below.
- `results`: bounded batches of completed task results, emitted immediately. Results remain pending until their IDs appear in `ack_results`; disconnects keep unconfirmed results for the next handshake.

Identity, mode, version and capabilities are inherited from the authenticated session; a heartbeat must not erase stored observations. A changed identity token is sent in an uncompressed update and checked against current credentials. Telemetry is not compressed when that token is present. Commands, arbitrary task results and credentials are never compressed together with telemetry. Reconnects repeat the complete v1 authentication and negotiation.

Commands execute serially and telemetry sampling runs in a separate worker; neither holds the heartbeat's state lock during a slow operation. The controller replies to updates, dispatching at most one command batch at a time. Command delivery normally remains bounded by the 5-second telemetry cadence; this extension does not introduce unsolicited command push. Results are acknowledged only after terminal task state is persisted. Configuration-mode changes wait for active commands and unacknowledged results to drain. Online status can use any authenticated update; Auto mode allows three 15-second heartbeat intervals before treating a negotiated WebSocket as stale, while legacy streams keep their old fallback window.

The implementation lives in `pkg/agentwire/{wire,stream,delta}.go` and the matching Agent `internal/wire` files, differing only in package name. Tests cover v1/binary compatibility, negotiation, sequence continuity, tampering, replay, decompression and reconstructed-state limits, complete idle counter samples, delayed ACKs, reconnect baselines and heartbeats during slow sampling/commands.

# Negotiated telemetry deltas

When both sides select `telemetry_delta: true`, each telemetry has `telemetry_seq` (starting at 1) and `delta: {base, full?, set?, removed?}` instead of `observation`. `base` is the last acknowledged telemetry sequence, initially 0. The first telemetry on every connection is full; a changed Xray stats generation also produces a full baseline. A full delta replaces the complete observation with `set`. Otherwise, `set` recursively updates object fields, replaces arrays/scalars, and `removed` explicitly lists deleted field paths as arrays of strings. JSON null is a value, not a deletion. Counter values remain absolute cumulative numbers; omission means unchanged within a complete sample, not missing collection.

The controller reconstructs the entire observation before running existing accounting and behavior rules. Sampling timestamps still advance for idle counters, so zero activity is distinguishable from missing samples. The wire baseline is immutable and separated from accounting's mutable input. Both encoded deltas and the reconstructed observation are bounded by the existing 16 MiB limit, with maximum observation nesting of 64. Numeric normalization preserves integer counter values. Wrong baselines or non-consecutive telemetry sequences close the connection.

Each accepted telemetry receives `telemetry_ack`. The Agent keeps at most one unacknowledged telemetry baseline, continues independent heartbeats/results, and coalesces subsequent cumulative samples while waiting. An ACK timeout of three heartbeat intervals reconnects. The ACK confirms the stream baseline; it is not a new transactional durability guarantee for the existing ledger. A reconnect always rebuilds a full baseline from the next fresh sample. Delayed sampling/ACKs still obey the existing gap detection rather than fabricating samples.

Negotiated replies omit unchanged interval/connection settings and empty commands; a plain heartbeat can receive `{}`. Telemetry and result ACKs, errors and commands are retained. Changed connection settings are repeated against the connection's original settings until the Agent applies them and reconnects, including while commands are busy. Peers that did not negotiate deltas retain the original reply encoding. The fixed 15-second heartbeat requirement is unchanged.

# Configuration snapshot refresh

The controller persists the Agent's `core.config.get` result `sha256` alongside the cached configuration and compares it with `observation.core.config_sha256`. It fetches the full configuration on first use, a changed hash, explicit manual sync, or successful apply/restore invalidation. Unchanged hashes do not trigger periodic full downloads, including after controller restarts. Failures for the same hash are throttled for five minutes; a new hash can be fetched immediately. Existing cache rows without a hash are refreshed once to establish a baseline. Agents that do not provide a usable hash retain the five-minute periodic fallback.
