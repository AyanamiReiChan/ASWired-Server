# 流量统计性能与一致性

v1.0.3 减少 SQLite 主控反复扫描流量台账的开销。Agent 上报周期、5 秒维护周期、原始台账、计费倍率、配额和超额限速规则保持原样。

## 实现

- 台账及索引只在数据库初始化/迁移时创建，普通统计和上报不再执行 DDL。
- SQLite 为每个订阅维护台账版本号。INSERT、UPDATE、DELETE 触发器在写入事务内更新版本号，事务回滚时一并回滚。恢复备份、其他数据库连接写入及旧版程序写入同样使缓存失效。
- 读取版本号和汇总使用同一个读取事务。只有订阅、周期边界和版本都匹配时才复用统计结果，最多保留 1,024 个订阅的结果。不缓存账户权限、有效期或限速决策，不使用 TTL。
- 汇总仍使用原来的两条 SUM 查询及索引，保留浮点求和顺序。无重置订阅保留原来的“当前时间加 100 年”边界；存在远期导入数据时重新计算，避免移动边界遗漏数据。
- 上报提交后只刷新本次产生台账记录的订阅显示字段。零增量上报仍推进游标和评估行为规则。维护任务补偿显示刷新失败，单纯更新显示字段不会触发用户配置重下发。
- PostgreSQL 不使用 SQLite 缓存或触发器，继续执行原有汇总查询。

## 本地基准

2026-09-22，Windows amd64、Ryzen 7 9800X3D、Go 1.27.1、modernc SQLite 默认连接配置。全部使用合成数据：82,203 条台账、9 个订阅，无生产数据。每项运行两次，每次至少 2 秒。

| 工作负载 | v1.0.2 / 原始查询 | v1.0.3 |
| --- | ---: | ---: |
| 整轮 `expireSubscriptions`，台账未变化 | 366.8–368.7 ms | 0.798–0.815 ms |
| 9 个订阅各查询 3 次，台账未变化 | 460.3–461.0 ms | 0.216–0.222 ms |
| 同上，每轮更新 1 个订阅的台账 | 原始查询约 461 ms（未计写入） | 19.6–20.1 ms（含写入） |

整轮维护基准使用同一份 `accounting_bench_test.go` 分别在 v1.0.2 和新代码运行。表中第二、三行的基线是原始两条 SUM 查询；不包含旧版重复 DDL，因此是保守比较。缓存预热后计时，冷启动或台账变化仍需查询台账。

```sh
go test ./internal/httpapi -run '^$' -bench BenchmarkExpireSubscriptions82203Rows -benchtime=2s -count=2
go test ./internal/store -run '^$' -bench BenchmarkTrafficUsage82203Rows -benchtime=2s -count=2
```

这些是统计路径的本地耗时，不代表线上 CPU 百分比。部署后的首次查询会重建内存缓存；持续有流量的订阅每次变化后仍完整汇总一次。大量订阅同时持续写入时，改善幅度会小于静态台账基准。

## 回归与升级

测试覆盖逐位一致的浮点结果、半开周期边界、远期数据、零增量行为评估、限额立即生效、外部连接写入、事务回滚、并发读取、旧数据库启动、重启、真实备份恢复，以及显示写入失败后的维护补偿。PostgreSQL 测试由 CI 的 PostgreSQL 16 实例运行。

升级只新增派生版本表和触发器，不重写历史台账。逻辑备份不包含派生版本表，恢复台账时自动推进版本；程序重启后从台账计算。性能回退可切回旧二进制并保留当前数据库；不要为性能回退恢复旧数据库，否则会丢失升级后的流量。
