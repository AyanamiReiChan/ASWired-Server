# 流量统计性能与一致性

v1.0.12 优化持续流量写入时的 SQLite 统计与默认行为限速资格检查。v1.0.3、v1.0.8 的历史实现与基准保留在下文。Agent 上报周期、5 秒维护周期、原始台账、计费倍率、配额和超额限速规则保持原样。

## v1.0.13：共享池复用增量统计

共享池汇总各成员已确定的计费窗口，个人展示继续使用个人窗口。两种窗口使用独立缓存键，避免首期转换或个人重置后相互挤掉同一订阅的缓存。一次上报、维护、权限重算或 HTTP 请求复用同一个池汇总；下一次操作重新读取台账版本，不跨操作缓存额度结论。共享汇总在一个数据库事务中读取池窗口、台账及当前实例数量。SQLite 复用下述近期尾部算法，PostgreSQL 使用事务内 SQL 汇总。

`TestTrafficPoolReusesIncrementalWindowsAlongsidePersonalCycles` 使用两成员、5,000 行历史和不同的个人/池周期，预热后连续追加 10 次并交替查询两种窗口，要求实际读取行数不超过 700；另检查历史修正后安全重建。该测试证明不会因两种窗口交替访问而重复扫描整段历史，不代表生产 CPU 的固定降幅。首次转换、重置、冷启动和超出缓存容量的套餐仍需重读相应窗口。

## v1.0.12：持续写入与近期乱序

订阅总量、上下行和逐节点统计在内存中保存 SQLite 的未最终合并的补偿求和状态。按 `(sampled_at,rowid)` 顺序保留较旧前缀，每次台账变化仅重读最近 60 秒的尾部，并严格按原账期 `[start,end)` 过滤；尾部重新排序可以吸收不同 Agent 的近期迟到及相同时间戳。不会把总量改为上下行之和，也不会直接累加已经求和、舍入的分桶结果。

冷重建会与原始 SQL SUM 逐位核对。数据类型或结果不适合该路径时继续使用原 SQL。较早的历史插入、UPDATE、DELETE、REPLACE、恢复和账期边界变化都可使前缀失效；极端历史乱序需要冷重建，其额外校验可能比原路径更慢。首次启动或旧库第一次写入也有预热成本。优化针对近期持续上报，不能保证所有工作负载都更快。

新增 `traffic_usage_windows` 保存订阅及订阅＋email 两种范围的派生版本、变更标记和最新时间。元数据由与台账同一事务内的触发器维护，覆盖外部连接、旧程序写入和回滚；REPLACE 的隐式删除冲突也会使被替换的旧范围失效。一个节点追加流量不会使同订阅其他节点的缓存失效。版本读取和统计使用同一快照，不缓存权限或额度结论，不使用 TTL。

迁移创建派生表和触发器，不遍历或改写原始台账；旧数据的最新时间通过原有索引按需读取。派生元数据不进入逻辑备份，恢复台账时按写入更新。内存统计每个范围最多 1,024 项，保存求和状态而非历史行。PostgreSQL 保持原有 SQL 汇总路径。

行为规则检查先选择当前服务器的候选节点，同次上报复用全局规则、套餐和节点资料；找到首个有效节点即可确认规则适用。保留共享的成员、套餐、订阅、额度、入站配置及中转校验，不单独复制一套简化权限判定。不同上报之间不复用配置快照，零增量采样、处罚触发与释放、5 秒维护周期保持原样。

### 验证方法与适用边界

- 计费差分覆盖补偿求和、浮点抵消、相同时间戳、近期/历史迟到、60 秒严格边界、缓存长期未读、外部连接、rowid/账号迁移、REPLACE、回滚、备份恢复、重启及移动账期结束时间。比较浮点位与额度结果，不只比较容差。
- SQL 读取探针验证超过 5,000 行的历史追加后只读取近期尾部；另一个节点写入时，未变化节点保持缓存命中。
- 行为检查覆盖 26 个资格等价场景、跨上报配置变更、零流量基线和无关服务器额度查询排除。
- 完整上报基准 `BenchmarkAccountStatsContinuous` 使用合成的 124 万和 248 万行历史、14 个订阅、10 个服务器、7 个活跃成员、默认均衡规则、一个套餐的两个节点额度。每轮通过真实 `accountStats` 新增 140 条流量台账，再执行维护，并与原 SQL 对账、验证 70 条行为状态。历史时间戳密集分布为每行 1 毫秒，保守地保留较大的近期尾部；不含生产账户数据。

```sh
go test ./internal/store -run 'TestTrafficWindow|TestTrafficUsage|TestNodeTrafficUsage' -count=1
go test ./internal/httpapi -run 'TestAccountStatsContinuousLedgerMatchesSQL|TestBehavior' -count=1
go test ./internal/httpapi -run '^$' -bench '^BenchmarkAccountStatsContinuous$' -benchtime=3x -count=1
go test ./internal/store -run '^$' -bench '^BenchmarkTrafficWindowContinuousWrites/82000/' -benchtime=3x -count=1
```

2026-09-30 的 Windows amd64 合成统计基准（82,000 行，每轮 9 个订阅、6 个节点，写入后查询总量、上下行和节点用量）中，原 SQL 约 377.19 ms/轮，顺序追加约 9.98 ms/轮，30 秒迟到约 18.16 ms/轮；120 秒历史迟到触发安全重建，约 563.07 ms/轮。该基准不含完整上报和行为评估，也不等于线上 CPU 改善。

应在相近业务负载下观察升级后持续上报的 CPU、处理延迟与读调用，尤其要确认没有持续历史乱序和反复冷重建。发布本版不自动升级已有主控或远端 Agent。

## v1.0.8：行为检查与逐节点额度

行为限速维护先检查状态是否包含待释放处罚。没有处罚时，不为释放检查重新展开该成员的订阅和节点；待处理通知仍按原流程处理。行为配置在节点查询前解析，未启用的配置可以提前跳过。存在处罚时，仍检查到期时间和配置变化；Agent 每次有效上报的计数、时间、核心代际和采样有效性继续维护，零增量上报也保留原有行为评估，不通过丢弃基线或放慢维护规避开销。

SQLite 的逐节点额度汇总按订阅、账号标识、周期边界和台账版本缓存。版本检查和 SUM 来自同一个读取事务；台账写入、修改、删除、外部连接写入或恢复都通过已有版本触发器使相关结果失效。缓存未命中仍执行原来的 `SUM(weighted_bytes)`，不改成增量浮点累加。无固定结束时间的订阅仍使用原有移动边界，并检查远期数据，避免缓存越过周期边界。

新增的 `(subscription_id,email,sampled_at)` 索引在初始化或迁移时创建，缩小逐节点 SUM 的扫描范围。索引不包含用于求和的 `weighted_bytes`，保留同一采样时间内的原始记录顺序；原始台账不重写。PostgreSQL 不使用 SQLite 的版本缓存，仍执行实时汇总。

这次优化不改变网页轮询、Agent 上报与 5 秒维护节奏，也不放宽成员权限、有效期或配额判定。冷启动、缓存失效和持续有流量写入的场景仍会执行 SUM。线上 CPU 降幅需在相近业务负载下测量，不能用查询基准承诺固定百分比。

## v1.0.3：订阅统计实现

- 台账及索引只在数据库初始化/迁移时创建，普通统计和上报不再执行 DDL。
- SQLite 为每个订阅维护台账版本号。INSERT、UPDATE、DELETE 触发器在写入事务内更新版本号，事务回滚时一并回滚。恢复备份、其他数据库连接写入及旧版程序写入同样使缓存失效。
- 读取版本号和汇总使用同一个读取事务。只有订阅、周期边界和版本都匹配时才复用统计结果，最多保留 1,024 个订阅的结果。不缓存账户权限、有效期或限速决策，不使用 TTL。
- 汇总仍使用原来的两条 SUM 查询及索引，保留浮点求和顺序。无重置订阅保留原来的“当前时间加 100 年”边界；存在远期导入数据时重新计算，避免移动边界遗漏数据。
- 上报提交后只刷新本次产生台账记录的订阅显示字段。零增量上报仍推进游标和评估行为规则。维护任务补偿显示刷新失败，单纯更新显示字段不会触发用户配置重下发。
- PostgreSQL 不使用 SQLite 缓存或触发器，继续执行原有汇总查询。

## 回归与升级

测试覆盖逐位一致的浮点结果、半开周期边界、远期数据、零增量行为评估、限额立即生效、外部连接写入、事务回滚、并发读取、旧数据库启动、重启、真实备份恢复，以及显示写入失败后的维护补偿。PostgreSQL 测试由 CI 的 PostgreSQL 16 实例运行。

升级只新增派生版本表和触发器，不重写历史台账。逻辑备份不包含派生版本表，恢复台账时自动推进版本；程序重启后从台账计算。性能回退可切回旧二进制并保留当前数据库；不要为性能回退恢复旧数据库，否则会丢失升级后的流量。
